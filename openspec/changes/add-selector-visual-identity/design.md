# Design

## Context

See proposal.md for motivation. The current working tree already contains file-based configuration, validated by an allowlist of property fields (`key`, `options`, `triggers`). `fillOptions` renders native select/option elements shared by Properties and Bases. CSS currently supplies sizing rather than semantic distinctions. The separate alias change contains only metadata.

## Goals / Non-Goals

Goals: retain native keyboard selection, distinguish three prompt states, preserve exact storage identity and provide explicit readable labels.

Non-goals: changing trigger execution, automatic title generation, translating labels, global property renames, styling unrelated properties, or rewriting Base definitions.

## Decisions

1. Use plugin-scoped CSS classes and theme variables for subtle borders/backgrounds, keeping the native select arrow and visible focus ring. Preserve the existing property-type icon. Whole-row color and color-only distinctions were rejected because they obscure status colors and make dense tables noisy.
2. Derive separate `has prompt` and `selected value has prompt` states from effective valid triggers. Following Hamed's 2026-11-20 refinements, toggle `smart-properties-prompt-icon` on the existing Properties `.metadata-property-icon` and supported Bases `.bases-table-header-icon` to set `--icon-color` and `color` to `--text-accent`. Preserve the same native nodes, SVG shapes (including the ordinary three-line icon) and their respective native interactions; do not replace icons or add listeners. Remove the property-level dot beside the name and its reserved label space. Configuration/trigger removal, unknown header binding and unload clear the relevant tint class. Retain a separate passive 5px dot beside a trigger-bearing selected value in Properties only. Bases has no additional header/property/value CSS dots, preventing crowding at cell edges. Header tint is independent of explicit/configured label resolution and appears whenever its safely bound property has valid triggers. No message icon or visible `Prompt` word is used. Mark each trigger-bearing option with the plain-text suffix ` •`, preserving its actual value. Native option rendering uses platform menu colors; textual suffixes retain native keyboard behavior and avoid a custom combobox. Explicit accessible explanations and textual option markers convey association independently of hue; forced-colors mode uses CanvasText for icons and CSS dots.
3. Provide accessible names/descriptions, but no custom visual prompt tooltip on hover or keyboard focus in this change; Hamed deferred the visible explanation. Preserve the property-level description `Some options have prompts. Selecting an option marked • asks for confirmation before opening a Copilot draft; it is not sent automatically.` through `aria-describedby`, with value-level wording `This value has a connected prompt`. Do not set a visible `title` for the prompt explanation. A marker is not a run button or a record of past execution. Loading a note with `done` displays its association without claiming its prompt ran.
4. Add optional `display_name`: trim nonempty strings, reject other supplied values using normal configuration validation, preserve the field in cache/export/reload, and keep schema version 1. Absence uses the exact key. Render labels as text, never HTML. Explicit labels avoid fragile underscore stripping, translation assumptions and `s.*` conventions.
5. In Properties, overlay a plugin-owned readable label while retaining native key editing. Following Hamed's 2026-11-20 refinement, labels inherit the normal font family and use Obsidian's native `--metadata-label-font-size`, `--metadata-label-font-weight` and `--metadata-label-text-color`, with the native input's normal line height. No larger/bolder styling or name/key hover tooltip is added. The native key input's title is suppressed only while decorated and its previous title restored on cleanup when no other title has appeared. Entering key-edit mode reveals the actual key; accessible control names retain the exact identity. Prompt guidance remains in an assistive-technology description with no visible hover/focus tooltip; ordinary controls have no explanatory description. In Bases use the explicit Base column display name when present; otherwise use configured `display_name`, then exact key. Do not rewrite `.base` files or add header/cell dots; textual option suffixes and accessible descriptions retain prompt information.
6. Synchronize decoration with options/current-value refresh, including reused Bases rows. Recompute after focus deferral; never rebuild focused controls unnecessarily. Restore original labels/editors and remove all owned wrappers, listeners and classes on configuration removal/unload. Label collisions are allowed because binding always uses the exact key; accessible control names expose that key.
7. Non-public dependencies: `.metadata-property*` and its key input, Bases table/header structures and row-link context; unsupported structures keep native editors and exact labels. An unsafe label overlay falls back to the exact name without losing a working dropdown. Copilot's internal `newAgentChatWithDraft()` remains behind full-prompt confirmation, with existing clipboard fallback. Styling must work without Copilot. No third-party code is required.

Implementation detail: recognize legacy `.bases-th[data-property]` and current `.bases-thead .bases-tr > .bases-td` headers. Prefer a direct property attribute; otherwise match the header's nonempty inline `insetInlineStart` and `width` against body cells carrying `data-property` in the exact same nearest `.bases-view`. Accept only a unique property key: never infer from column index or visible label. This follows the shared header/body virtualization geometry in the installed Obsidian 1.15.1 code. Empty or ambiguous matches preserve the native header. Prefer the dedicated `.bases-table-header-name`; its outer label contains the native icon and must not be overwritten. Clear owned state on unknown/reused bindings or replaced label nodes. A standalone Base's optional `getViewData()` method is treated as an internal capability; otherwise the identifiable `.base` file is read through the vault API. Linked embeds resolve their source file; inline Bases with an unknown source retain native names. An explicit `displayName` or legacy `display:` mapping under either the raw property key or `note.<key>` takes precedence, even if it equals the exact key. Unknown source, invalid data or unsupported header markup uses the native label; the accessible control name still exposes the readable name and exact key. Each control references a visually hidden identity span through aria-labelledby, avoiding Obsidian's automatic visual tooltip from aria-label; prompt-only help uses a separate aria-describedby target. Both spans are owned decorations removed with the control.

Properties label alignment: the absolutely positioned readable overlay uses `inset-block-start: 50%` and `transform: translateY(-50%)` to center its own text line within the native key host. This follows row height without a fixed pixel correction and preserves native font metrics, inline ellipsis and focus-to-edit behavior.

Bases explicit-name rendering: resolve the actual explicit string from current `properties.*.displayName` or legacy `display:` entries under full/raw keys, rather than skipping decoration merely because the field exists. The installed native parser can store shorthand property definitions under raw keys while the view looks up full keys. If the header is still raw and the explicit name is unambiguous, render that name; otherwise use the plugin display name only when no explicit field exists. Conflicting or invalid explicit definitions and foreign readable text preserve native presentation. No Base-file rewrite is needed.

## Risks / Trade-offs

- Native option suffixes consume width -> keep them short; the accessible description supplies the full explanation.
- A visual prompt tooltip is omitted from this change at Hamed's request; consider it separately in a later change if needed.
- Another plugin controls grouping/labels -> preserve foreign DOM and native type icons; prefer existing explicit Bases labels and fail back to exact keys if ownership is ambiguous.
- Dark/light themes and compact tables -> retain theme variables and logical spacing. Hamed confirmed English property names for acceptance; dedicated Persian-label/RTL-layout certification is outside this change's acceptance scope. Existing configuration string support and logical CSS remain unchanged.
- Configuration work is uncommitted and not reflected in canonical specs -> apply after its approval/completion and reconcile its schema delta with this additive requirement. Do not overwrite its work.
- Older plugin builds reject the new field -> document that configs using `display_name` require this release; roll back labels by removing the field before installing an older version.

## Migration Plan

After approval, implement on the reconciled file-configuration baseline, update README/example and the next appropriate manifest/versions entry, then review in Obsidian before deployment. Existing configs without display names require no migration. Retire the obsolete alias scaffold during implementation, not during this planning task. No YAML property migration is required. Rollback removes plugin decorations and restores exact keys/native editors without note writes.
